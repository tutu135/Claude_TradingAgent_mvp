二、工作原则

1. 只依据当前能够读取的真实材料，不得根据通用金融知识编造内部流程或专家规则。
2. 不确定的信息统一标记为 UNKNOWN 或 TBD，并说明需要由谁、通过什么材料确认。
3. 区分以下四类内容：
   - 已由正式制度、SOP 或系统文档确认的规则；
   - 从多个高质量历史案例中归纳出的稳定经验；
   - 从单次对话、单份报告或个人表达中提取的候选经验；
   - 模型推测。模型推测不得写入正式规则，只能放入待确认清单。
4. 历史模型对话、人工批注和修改记录是一等资料来源：贵方投研流程大量依托模型工具完成，这些对话记录中沉淀了真实的操作步骤、判断依据和纠偏过程，请主动从中复原人工流程和专家经验，并按第 3 条分级。
5. 每条规则、流程和判断尽可能标注来源文件、文档日期、页码、章节、对话时间或系统名称。
6. 不输出任何 API Key、密码、Cookie、Token、个人账号或真实访问凭证。
7. 对涉及个人信息、持仓、交易记录、重大未公开信息或其他敏感内容进行脱敏。
8. 不输出买入、卖出、持有、仓位或交易操作建议。
9. 不要因为资料不完整而停止。先完成可确认部分，再生成缺失项和补充问题清单。

三、第一步：复原真实投研任务清单

从历史报告、SOP、对话、批注和操作记录中识别实际执行过的投研任务，生成 task-catalog.yaml。至少检查：

- 赛道或行业研究；
- 两标的对比；
- 财报解读；
- 事件影响分析；
- 长篇研报摘要；
- 风险核验；
- 股票池或组合跟踪；
- 假设复查和复盘。

每个任务记录：

- task_id
- 任务名称
- 使用场景
- 使用人员
- 触发方式
- 输入数据
- 输出形式
- 当前人工耗时
- 频率
- 时效要求
- 准确性要求
- 可解释性要求
- 优先级
- 是否适合首期实现
- 典型样例来源
- 当前确认状态

四、第二步：复原人工流程 SOP

为每类任务生成单独的 SOP，并汇总为 sop.md。不要只写概括性步骤。每个步骤必须包含：

- step_id
- 步骤名称
- 执行角色
- 输入
- 使用的数据源、系统、API 或文档
- 实际操作
- 使用的固定规则
- 依赖的专家判断
- 输出
- 完成标准
- 人工耗时
- 常见错误
- 异常和例外处理
- 交叉验证方式
- 复核人或复核方式
- 可自动化程度
- 证据来源
- 当前确认状态

重点回答：

1. 分析师拿到一个问题后，第一步实际做什么？
2. 如何决定需要查哪些指标、文档和公司？
3. 数据冲突时优先相信什么，为什么？
4. 哪些环节是机械规则，哪些依赖专家判断？
5. 哪些情况下会回头补取数据？
6. 哪些数字必须回到原文核验？
7. 如何选择可比公司？
8. 如何判断业绩驱动、预期差和风险？
9. 如何主动寻找反方证据？
10. 什么情况下宁可不写结论？
11. 报告初稿如何复核、修改和批准？
12. 哪些错误曾经导致报告质量明显下降？

同时生成 process-flow.mmd，使用 Mermaid 表达：用户输入 -> 任务拆解 -> 数据获取 -> 数据清洗和口径处理 -> 信源核验 -> 专家分析 -> 反方验证 -> 报告生成 -> 人工复核 -> 后续跟踪。

五、第三步：提取专家经验和判断规则

从 SOP、投研笔记、优秀报告、失败报告、历史对话、人工批注和复盘记录中提取经验，生成 expert-rules.yaml。

每条经验必须采用以下结构：

- rule_id
- 规则名称
- 适用行业、公司类型或任务
- rule_type：hard_rule、configurable_threshold、heuristic、warning、example
- 触发条件
- 需要观察的指标或证据
- 判断步骤
- 预期输出或动作
- 例外情况
- 反例
- 常见错误
- 纠偏方式
- 可观测证伪条件
- 来源文件、报告、对话或批注
- 来源日期
- evidence_count
- confidence：confirmed、probable、candidate、unconfirmed
- 需要谁确认

特别提取：

- 半导体与 AI 资本开支链分析时优先看的指标；
- 不同产业链环节的关键经营指标；
- 业务纯度、壁垒、利润率、客户集中度、产能、单位价值量、技术路线风险和估值位置的判断方法；
- 公司公告、管理层指引、研报观点和专家纪要的不同使用方式；
- 供应链关系和供应占比的核验方法；
- 海外公司与 A 股公司的映射依据和不可比点；
- 订单、认证、产能和收入之间的实现度判断；
- 典型错误、模型过去犯过的错误和人工纠偏方法；
- 必须主动提出的反方问题和证伪变量。

禁止把一次性的个人观点直接写成 confirmed 规则。只有正式制度明确规定，或得到负责人确认的内容，才能标记 confirmed。

- 主要问题
- 文件位置

生成 report-spec.md，说明不同报告类型的：

- 必填章节；
- 必填指标；
- 事实、观点和假设的表达方式；
- 数字来源和时点标注格式；
- 风险和反方观点要求；
- 不可接受内容；
- 输出格式；
- 人工复核要求。

生成 evaluation-rubric.yaml，至少包括：

- 事实准确性；
- 数字和口径准确性；
- 来源完整性；
- 信息完整性；
- 逻辑一致性；
- 专业性；
- 观点是否有证据支撑；
- 可解释性；

每个维度给出评分范围、合格标准、优秀标准、不可接受条件和正反例。

七、第五步：以示例股票完成全链路案例（强制验收项）

5. 如果该股票存在已完成的历史人工报告，优先重放该历史案例，并保留人工原始输入、初稿、修改意见和终稿之间的关系。

- 当前最重要的公司经营指标、行业指标和预期变量是什么？

八、第六步：生成投研方法论 Skill（强制验收项）

在 investment-research-skill/ 中创建一个标准 Skill。这是本次交付的核心产物之一：接收方的模型将直接安装这个 Skill，用它理解贵方的投研方法论。Skill 的目的不是保存实时数据或替代 API，而是让接收方的模型掌握：

- 有哪些投研任务，每类任务的执行流程是什么；
- 每类数字应该用什么口径、有哪些常见陷阱；
- 不同信源（公告、管理层指引、研报、专家纪要）分别怎么用、什么能当事实什么只能当观点；
- 哪些规则是硬规则，哪些是可配置阈值，哪些是专家启发式；
- 报告必须满足什么结构和评价标准；
- 必须主动提出哪些反方问题和证伪变量；
- 证据不足、权限不足或规则未确认时如何停止并提出问题。

  SKILL.md

    normalization-traps.md
    source-usage.md
    expert-rules.md
    report-templates.md
    evaluation-rubric.md

要求：

1. SKILL.md 使用合法 YAML frontmatter，包含 name 和 description：
   - name 使用小写字母、数字和连字符（例如 investment-research-methodology）；
   - description 清楚说明何时应触发此 Skill（例如"当用户要求进行单标的研究、赛道研究、两标的对比、财报解读或报告质量审查时"）。
2. SKILL.md 主体只保留：任务识别、每类任务的核心工作流、references/ 文件的路由说明（什么任务读哪个文件）、不可违反的硬规则、停止条件。控制在 500 行以内。
3. 详细内容放入 references/，不在 SKILL.md 中重复：
   - task-workflows.md：每类任务的分步流程（来自 sop.md 的提炼）；
   - normalization-traps.md：数字口径判别规则和真实陷阱案例；
   - source-usage.md：各类信源的使用方式、事实/观点边界、冲突裁定方法；
   - expert-rules.md：专家判断规则（来自 expert-rules.yaml，保留 rule_id 和 confidence 标注）；
   - report-templates.md：报告结构、语言要求、正反样例；
   - evaluation-rubric.md：评分维度与合格/优秀/不可接受标准；
