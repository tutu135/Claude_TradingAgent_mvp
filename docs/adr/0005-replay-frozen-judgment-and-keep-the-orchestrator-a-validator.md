# 黄金案例以冻结重放执行，编排器只做裁判不做指挥

Ticket 06 要同时满足两条互相拉扯的要求：票面第 7、8 条要求"端到端运行证明"，而 ADR 0004 已经接受"分析产物不是位级可重建的"。若把"端到端"读成"每次真调模型"，06 唯一的硬验收就会消失；若含糊带过，后来的人迟早会把模型调用塞回编排器。因此本 ADR 冻结两件事：**黄金案例运行的执行模式**，以及**编排器与工作流引擎的分界线**。

## 决定一：`DEMO_RUN` 的唯一执行模式是 `FROZEN_REPLAY`

模型判断产物（`findings-attempt-{1,2}.yaml`、`challenges-model.yaml`）升格为**冻结判断输入**：只读、入库、带哈希与完整绑定，与研究材料同受哈希保护但审计语义不同——前者是证据输入，后者是受治理的判断。编排器不重新生成它们，运行过程中不发生任何模型调用。票面第 7、8 条判定的对象因此是**从冻结输入到最终产物的确定性重放**：两次从干净运行目录执行，`report.md` 与 `manifest.yaml` 哈希一致，manifest 中全部受管产物哈希一致。

判断层本身的可信度不由端到端承担，而由 ADR 0004 已经冻结的机制承担——`analysis-validation.yaml` 的逐项校验加 `analysis-attempts.jsonl` 的全过程留痕。06 不重开这个已经做过一次的决定。

否决"每次真调模型"的依据是实测而非偏好。模型判断在链路上有两个注入点，下游是六个权威文件（`findings.yaml`、`analysis-attempts.jsonl`、`analysis-validation.yaml`、`challenges.yaml`、`findings-revised.yaml`、`gaps.yaml`）而不只是报告；`evidence_score` 由脚本从模型选中的证据反算，因此变的不是措辞而是结论与分数——质询已经真实翻转过 D2 `SUPPORTED→MIXED` 与 D7 `MIXED→UNKNOWN`。更关键的是 05 的实测首轮拒绝率为 **3/7**（D1/D2/D3 因未归因因果连接词被拒），而每维只有两次机会，第二次失败即强制 `UNKNOWN`/`evidence_score=0`/`analysis_run_status=FAIL`。真调模型会让票面第 7、8 条一次 PASS 一次 FAIL——不可复现的验收条件不是验收条件。此外 `manifest.yaml` 的哈希清单会退化成装饰品，而契约地图明写哈希用于"重现与防止静默改写"。

代价如实记录：判断层没有在端到端运行中被执行过。这个取舍可逆且成本很低——模型输出文件本身就在磁盘上，切换执行模式不销毁任何东西。为保持它便宜，报告正文一律不嵌入哈希或执行模式相关内容，渲染层与执行模式解耦。

绑定只设两道闸加一项登记，不设七项。`selection_hash` 已经传递性覆盖 `snapshot_id`、`context_rule_version` 与选取规则，`rules_hash` 覆盖分析规则；prompt 由脚本从候选集与规则确定性拼装，属导出量不是独立量；`analysis_schema_version` 不存在的原因是 05 的逐次校验已经拒绝不合规输出，能被冻结下来的输出按构造即 schema 合法。模型标识只登记不设闸——它不可校验，做成闸门是假闸门。

## 决定二：编排器是 Skill，脚本只是裁判

七阶段固定顺序是**知识**，写在 `single-stock-research-orchestrator` 的 Markdown 指令里，是文本常量而不是可配置的 DAG。停止、降级与哈希是**确定性判断**，写在薄脚本 `scripts/validate_demo_run.py` 里，只有 `preflight`、`gate`、`finalize-manifest` 三个子命令。**该脚本不 import 任何阶段脚本、不 subprocess 调用它们、不包含"下一步是什么"的控制流**；每个阶段仍由 Skill 指令显式调用各自的 CLI。

分界线定在这里的理由是：一旦顺序进入脚本的控制流，哪怕当前只有七步固定，它已经是步骤执行器了，而票面第 2 条禁止通用 DAG、队列、调度器、数据库、模型路由与插件系统。脚本命名同样是防线——`validate_` 让"它只是裁判"写在文件名上，`orchestrate_` 会持续邀请后来的人往里加编排。

## 决定三：永远有报告，但完整性失败不得带结论

不存在"编排器静默停止"这回事。`report.md` 恒被生成，只有两种形态：`FULL_REPORT` 按 FR-070 固定十章节展示研究发现；`DIAGNOSTIC_ONLY` 在完整性失败时生成，顶部为显著失败横幅，正文只含失败诊断、reason code 与 gap 引用，**不含任何 D1–D7 结论**。两者同名同路径，形态记入 `manifest.yaml`，且恰好两种不留第三种口子。

区分依据是失败的性质而非严重程度。**完整性失败**（冻结判断输入缺失/哈希不符/绑定不符、快照身份不符、运行目录出现清单外的 `.yaml`/`.jsonl`/`.md`）意味着输入不可信，此时手里的发现是否由当前规则产出都无法确认，照常输出带结论的报告会产出一份自我矛盾的文件——声明自己不可信却通篇陈述发现，且违反 FR-072「治理失败时受影响数据不能支撑研究发现」。**内容级失败**（任一 run status 为 WARN/FAIL、`governance_status=FAIL`）则输入可信而结论不合格，按 FR-072 与票面第 5 条照常出报告并显著标警。完整性检查发生在消费任何输入之前，此时尚无产出，停止的代价为零。

`governance_status` 只由检索、规整与证据治理三个状态按最坏值合成；分析与质询状态不并入，各自原样展示。理由是治理与分析在 Spec 里是两条不同的概念轴——ADR 0004 专门把分析层的保证从哈希移到校验，它不属于治理；FR-072 也只要求一个 `governance_status`，造跨轴总状态会同时丢信息和混淆语义。
