框架总览把「可核验」做成工程约束

用一份冻结的真实公开资料——中芯国际 20 份年报 / 季报 / 电话会纪要——跑通一条从原始 PDF 到研究报告的完整流水线，验证一件事：报告里的每一个数字，能不能都追溯回原文的确切位置。

为什么这不是「把年报丢给 GPT」

大模型能写出流畅的研报，问题是你无法逐个核验里面的数字——真数字和幻觉数字长得一模一样。 这个项目的做法不是「让模型少犯错」，而是把可核验性变成结构上无法绕过的约束：

三个机制

  • 溯源链：每个数字都带 evidence_id → fact_id → chunk_id → material_id， 能一路点回「哪份材料、第几页、哪一章」。
  • 整句排除：模型写的叙述里，凡是带了数字但那个数字没有对应证据行的，整句删除—— 不是把数字抹掉。抹字符会留下「毛利率由上升到，改善个百分点」这种看起来还像人话的垃圾。
  • 最终门禁：报告渲染完之后，程序回读这个文件，扫自由叙述区，断言未绑定数字数量为 0。

代价很直白，也已经量化在上面那张卡片里。项目的立场是难看但可核验 > 好看但不可核验。

三个可能有意思的设计决定

1 · 材料不会自动变成证据

进快照的材料统一标 ACQUIRED_UNASSESSED。采集只管「有没有出处、时间对不对、 字节能不能哈希复现」，完全不判断真假。能不能拿来支撑结论是后面独立一层的事。 这样「我找到了这份资料」和「这份资料可信」就不会被偷偷合并。

2 · 模型判断被夹在两层确定性逻辑中间

选证据是确定性脚本（按检索分数和来源多样性挑，有预算上限）；模型只在中间做一次有界判断， 且只能引用给定候选集里的 ID，引用集外的直接判失败；证据分由脚本从模型选中的证据反算， 模型不产出分数。实测首轮有 3/7 个维度因为「因果措辞没有标注来源」被拒绝重来。

3 · 端到端不重新调模型（这条最容易被质疑）

模型的判断产物被冻结成只读输入，跑流程时零模型调用。所以「端到端可复现」证明的是 从冻结输入到最终产物的确定性重放，不是判断层被重新执行。

这么选的原因是实测的：每个维度只有两次生成机会，第二次再失败就强制 UNKNOWN。真调模型会让 同一份验收一次通过一次失败——不可复现的验收不是验收。判断层本身的可信度由 12 项校验 加全过程留痕承担。代价已如实记录在 docs/adr/0005。

这一步拦住了什么

  • 时间晚于 as_of 的内容——已确认晚于 as_of 的直接不进快照；发布时间区间跨越 as_of 的也不进。
  • 拿不出出处的内容——采集来源、展示发布主体、发布时间依据、材料定位，缺任何一项就留在快照外的候选材料暂存区，不分配 material_id。
  • 字节不可复现的内容——每份材料记录 sha256 内容哈希；相同哈希只创建一个 material_id，转载入口作为备用定位。
  • 把「找到了」升级成「可信」——这是最关键的一道。所有材料统一 ACQUIRED_UNASSESSED，采集阶段不做真假判断、不评信源等级、不判证据资格。

这条分离是有意为之的架构决策（ADR 0002）。合并的诱惑很大：既然都费劲找到了， 顺手标个「可信」多方便。但一旦合并，后面就再也分不清「这个结论站得住是因为证据强」还是 「因为我当初找资料时觉得这来源不错」。

深入：两种运行模式，以及为什么快照不能原地更新

SNAPSHOT_BUILD 可联网采集；DEMO_RUN 只读冻结输入， 绝不联网、绝不接受晚于 as_of 的材料。本 Demo 的端到端跑的全是 DEMO_RUN。

每个快照必须自包含。更新材料、采集元数据或规则时生成新的 snapshot_id， 不得原地伪装成同一快照。所以有 v1 / v2 / v3 三代，前两代不可变地保留着。 下游产物不写回快照目录——写回会破坏它的自包含冻结身份。

搜索状态只允许 IN_PROGRESS 或 SATURATED， 不允许用 COVERED / PARTIAL 声称事实完整——「我搜不动了」和「这件事没有更多资料」是两回事。

为什么这么设计——是工具默认就长这样吗

不完全是。pdfplumber 原生就暴露 bbox 和逐行文本，这套设计直接沿用了它的坐标粒度，没有再发明一层抽象。在此之上做了四个有意的选择：

  1. 保留按页 + bbox 的粒度，是为了满足"报告里引一个数字必须说清第几页、页面哪个位置"这个硬需求——从现成能力里挑出来保留，不是重新造。
  2. HTML 用标签序号而不是坐标：HTML 没有固定的页面像素概念，"标签[序号]"是最自然也最稳定的定位方式（同一份 HTML 每次解析序号一致，可复现）。
  3. reliable_text_layer 是项目自己加的字段，作用是触发 gap 记录而不是上 OCR：为 false 或某页解析失败时，计入 manifest 的 parse_unsupported / parse_partial 并写进 gaps.yaml，而不是硬着头皮猜内容。
  4. 两套 schema 刻意不统一：PDF 和 HTML 的"可定位单元"天然不同（像素坐标 vs 标签序号），硬做一个大而全的统一 schema 反而是过度抽象。阶段 2 分别处理这两种结构就够了，不需要通用适配层。

一句话：解析器的原生输出粒度 + 项目自加的两类字段（reliable_text_layer 触发 gap、*_candidates 给下游噪声识别提供线索）， 没有引入额外的通用抽象层——对应 AGENTS.md 的"不为可能的复用做抽象"。

做什么

写在运行目录，绝不写回快照——写回会破坏快照的自包含冻结身份。

这一阶段同样不判断真假。检索结果只是候选上下文， retrieval_status=PASS 只表示"检索这个动作质量合格"， BM25 分数不代表信源可信度，也不代表证据强度。

用一句话说清这一阶段

你手上有 20 份文件、几千页。下一阶段（事实规整）要把每个数字拆成值、单位、币种、期间、会计准则…… 建档非常贵，不可能对几千页全做。所以这一阶段就是个分拣员：

它只做两件事

  • 把几千页剪成一张张可以单独引用的小卡片（分块）——共 3,399 张
  • 用一组冻结的关键词，在可能有用的卡片上贴便利贴（检索 + 标记）——贴中 415 张

它不扔任何一张卡片，也不判断卡片上写的是真是假。下一阶段只精读贴了便利贴的那 12%。

这一步拦住了什么

  • 运行时改写查询——查询族是版本化的中英文子查询（31 个），各自独立跑 BM25 再取并集。 禁止模型临时扩写同义词、改写查询或改变固定查询集。否则每次跑出来的候选集都不一样， 「可复现」直接不成立。
  • 固定长度滑窗切碎表格——用结构原子分块。 表格片段必须共同携带表头、单位、期间和脚注，大表按行组拆分时重复携带这些解释要素—— 否则「20.1」就只是个孤零零的数字。
  • 静默删除噪声——导航、Cookie 提示、页脚这类结构噪声仍然保留在 context.jsonl 里， 只是固定标 candidate_context=false 并记录 filter_reason。删掉就无法解释为什么没被检索到。
  • 用信源等级做过滤——过滤只能识别结构性噪声，不得使用信源等级、内容类型、可信度、 观点方向或证据资格。那些是下一层的职责。

11 个 MUST 和 11 个 SHOULD 正好是每个查询族各一条（8 研究族 ＋ 3 护栏族）。 两条负控都来自 2026 Q1 那份第三方纪要网页：一条是页面购买引导按钮，一条是版权页脚。

先分清召回率和精确率

用捞鱼打比方：

问的是变差的表现
Recall 召回率该捞的鱼，捞上来了吗？漏网——有鱼没捞到
Precision 精确率捞上来的，都是鱼吗？捞了一堆水草——不相关的混进来

两者天然对立：网眼开大召回上去但精确率掉，网眼收紧精确率上去但会漏。所以要同时看。

① MUST_HIT Recall — 为什么不允许打折

这 11 条是人工判定"没有它就没法回答问题"的位置。漏一条，那个维度的分析就建立在残缺证据上了。 注意判定条件是 直接命中——靠邻接扩展蹭进来的不算数。 你不能说"我虽然没找到它，但找到了它旁边那块"。

② SHOULD_HIT Recall（总体）— 为什么门槛只有 80%

SHOULD 是"找到更好、漏了也能活"的补充内容。它存在的目的不是当闸门，而是量化已知漏召回—— 让你知道"我大概漏了两成"，而不是假装没漏。低于 80% 只是 WARN，允许继续跑，但漏掉的必须写进 gaps.yaml。

③ SHOULD_HIT Recall（任一查询族）— 防平均数骗人

假设总体 80% 达标了，但漏掉的 20% 全集中在 D7 一个族——那 D7 这个维度实际是瞎的，总体数字却很好看。 所以额外要求每一个族单独看都不能低于 60%，检索记录里逐族列出。

④ Precision@min(5,N) — 这个古怪写法什么意思

N ＝ 这条子查询实际返回的合格直接命中数； min(5,N) ＝ 取 5 和 N 里小的那个。 合起来：只看这条查询排名最靠前的那几条（最多 5 条），里面有几条是真的相关。

为什么只看前 5：下游真正用到的就是排名靠前的，第 18 名相不相关影响很小； 而且每一条被评估的命中都必须有人工判断，全标要标几千条。 N=0 时 Precision 记为 0——什么都没返回不算"没犯错"，算彻底失败。

⑤ NEGATIVE_CONTROL — 唯一在测"闸门本身有没有工作"的指标

其余七条都在问"你找到该找的了吗"，只有它在问"你有没有把不该要的放进来"。 那两条负控是故意放进考卷的陷阱——它们就混在纪要正文里，而且含 buying 之类的词，BM25 很可能命中。

判定条件的微妙之处

它算的是 candidate_context，不是 direct_hit——也就是说： 允许被检索命中，但绝不允许成为候选。

实际就是这样：那两块被查询命中了，但因为先被判成 STRUCTURAL_BOILERPLATE， selection_reason 记为 STRUCTURAL_BOILERPLATE 而不是 DIRECT_HIT，candidate_context 保持 false。 命中记录照样留着，只是不放行。

⑥ MUST_HIT 的定位准确率 — 它体检的是分块，不是检索

容易被误读成"找对文件了吗"。不是。它问的是： 考卷上写的那个位置（第 4 页第 1 张表），在实际切出来的 3,399 个片段里， 能不能唯一地解析到一个片段——代码判定是 len(matches) == 1，必须恰好一个。

结果说明什么
匹配到 0 个分块把那个位置切没了，或定位信息丢了
匹配到 2 个以上定位不唯一，说不清是哪一块

两种都算失败。这条挂了说明 chunk 的 content_locator 不可靠，整条溯源链就断了。

⑦ 数值类 MUST_HIT 的上下文完整性

带 required_numeric_context 的标注，会额外检查那个片段是否真的携带了 表头、单位、期间、脚注四样。这是"19.3% 不能变成孤零零一个数字"这条要求的自动化验收。

⑧ 两次干净重建的哈希

脚本在同一次运行里把整个分块 ＋ 检索完整做了第二遍，然后比对两次结果的哈希—— 不是靠人跑两次对比，是内建的：

chunks = build_chunks(...) # 第一遍 query_results = apply_retrieval(chunks, rules) second_chunks = build_chunks(...) # 第二遍，从头再来 second_query_results = apply_retrieval(second_chunks, rules) # 比对两者的哈希

这条挂了就说明代码里有非确定性（集合遍历顺序、时间戳、随机数……），整个"可复现"的承诺就塌了。

三个具体的折扣：

  1. 考卷只有 24 条，而且是知道语料长什么样之后标的。它是回归测试的基线，不是独立的能力评估。
  2. 精确率那 155 条人工判断全是 relevant: true，没有一条 false—— 这个指标在本次运行里完全没有展示出区分能力。结论仍然成立（前 5 名确实都相关）， 但别把"100%"理解成"这个闸门很严"。
  3. PASS 只评价检索这个动作。规则原文："不评价事实正确性、信源等级、内容类型、证据充分性或报告资格； PASS 结果仍只是候选上下文，不能成为治理证据或发布依据。"

为什么要分块：一个 19.3% 是怎么变成废数据的

大多数 RAG 的做法是滑窗：每 512 个 token 切一刀。这个项目明确禁止。看一个真实的 chunk 就懂—— 2023 年报第 16 页的这张表被完整切成一个片段：

SECTION 3 CORPORATE PROFILE AND PRINCIPAL FINANCIAL INDICATORS 2023 2022 2023 as compared with 2022 (%) 2021 Gross margin 19.3% 38.0% Decreased by 18.7 percentage points 30.8% Net margin 17.8% 30.2% Decreased by 12.4 percentage points 32.6% EBITDA margin 64.3% 63.4% Increased by 0.9 percentage point 70.2% Basic EPS $0.11 $0.23 -52.2 $0.22

现在想象滑窗在 Gross margin 那一行中间切了一刀，你会得到两块： 前一块是表头 2023 / 2022 / 2021 加半行； 后一块是 19.3% 38.0% ... 30.8%。

后一块里的 19.3% 就永久地失去了意义。它是哪一年的？是毛利率还是净利率？是百分比还是百分点？ 没人知道了——而下一阶段会照样把它抽出来建档。于是证据库里多了一条来源不明的 19.3%。

深入：为什么禁止运行时改写查询（四个理由，从硬到软）
  1. 改写会直接杀死可重放性。整个项目的核心命题是"两次干净重放，产物字节一致"。 如果运行时让模型说"用户在问盈利能力，我加两个同义词吧"，那这次跑出的 415 个候选和下次就可能不同， 下游 20,114 条事实、证据、发现、报告全会漂。LLM 即使 temperature=0 也不保证跨版本、跨时间稳定， 而下游挂着一条端到端的 sha256 链。
  2. 改写会让"检索验收"失去意义。那堆 1.0 是在一组固定 query ＋ 一组人工标注的标签上算的。 query 若是运行时生成的，验收测的就不是"这套检索规则行不行"，而是"这次模型心情如何"——指标不可比，回归测试也无从谈起。
  3. 改写会偷偷绕开 as_of 和快照边界。一个能自由扩写 query 的模型，会把它训练数据里知道的 "中芯 2026 年怎么样"写进检索词。它检索的仍然是快照里那 20 份材料没错， 但检索意图已经被未来信息污染了——它会有针对性地去捞能印证它已知结论的段落。 这是一种很隐蔽的前视偏差。
  4. 查询词本身是需要被审查的资产。现在可以打开 YAML 逐条看"我们到底问了什么"， 甚至可以指责"D3 的中文 query 没写晶圆收入结构"。这是可审计、可 diff 的。 运行时生成的 query 只存在于某次日志里，review 不了。

Spec 并没有把这条路永久封死，而是给了一条有闸门的口子：只有 BM25 为 WARN、 且预先登记了具体的词法漏召回，才允许在同一集合上做一次实验。目前是 PASS，所以这条口子根本没打开。

深入：为什么是 BM25 而不是向量检索

先说 BM25 是什么：词频加权的关键词打分。一个片段里出现"产能利用率"次数越多分越高； 但这个词若在 3,399 个片段里到处都是，权重就被压低（IDF）；长文档还会被长度归一化。 全部是可手算的确定性算术。

#理由
1确定性——压倒性的理由。BM25 分数是纯算术，同输入永远同输出。真实产物里能看到 score: 19.391288607163 这种十二位小数（代码固定精度），排序钉死为 score desc, chunk_id asc。向量检索则依赖一个 embedding 模型：模型版本、推理后端、 甚至浮点累加顺序一变，相似度就漂，Top-K 边界上的片段就换人——而边界直接决定那 415 个候选是哪 415 个。
2可解释、可审计。BM25 命中能指着说"因为这片段里有产能利用率和固定成本这两个词"， 所以 context.jsonl 里存得下 retrieval_keywords 和 selection_reason。 向量命中只能说"余弦相似度 0.83"——为什么 0.83？没人能回答。
3这个场景的词法特征太强，语义泛化反而是负担。要找的是"毛利率""profit from operations""IFRS""第三季度""US$ thousands" 这类精确术语，几乎没有同义改写空间。而向量检索的弱点在这里真的疼：它分不清 8 英寸 / 12 英寸（语义极近，业务上完全不能混）、分不清百分比变化 / 百分点变化、分不清 2025 Q3 / 2025 Q4 ——这些恰好都是项目列为硬错误的东西。
4中英混合语料上通用 embedding 不可控。而 BM25 只要给一份自定义词典就行—— 规则里那 44 个中文词条（产能利用率、等值晶圆、重新列报……）就是在告诉分词器"这些是不可切分的整体"。 这份词典是人写的、可读的、可 diff 的。
5简约原则。Spec 明确禁止建向量数据库服务、长期知识库、增量同步、重排服务、检索 API。 BM25 索引可随时删掉从材料重建——验收里 clean_rebuild_hashes_match: true 就是在验这个。
6最实际的：BM25 已经 PASS 了。Embedding 的触发条件写死为"BM25 为 WARN 且实验前已登记具体词法漏召回"。 既然基线满分，加向量能改善的空间是零，只会引入不确定性和依赖。BM25 若为 FAIL， 也是先去修分块、查询、词表或定位，而不是换检索方式掩盖问题。

那堆 1.0 要打个折扣看

它是在一份自己标注的、24 条标签的固定集合上算的，而标签是知道语料长什么样之后标的。 它证明的是"这套固定查询在这批固定材料上不漏关键段落"， 不是"BM25 在财报检索上普遍优于向量"。这两句话差别很大，别在汇报时混掉。

分词器固定保留的领域符号

IFRS、CAS、USD、R&D、EBITDA、晶圆尺寸、制程节点。并且把 4Q25、Q4 2025、2025 Q4 三种写法归一到同一个规范期间 token——这类归一化必须写死在分词器里，不能靠模型临场理解。

截断规则

每个子查询取全局 Top 20，同一材料最多保留 5 个直接命中，排序固定为 score desc, chunk_id asc。第 20 名同分时保留全部同分片段，但单材料上限仍生效。 不设跨查询的绝对 BM25 分数阈值，也不比较不同子查询的原始分数——BM25 分数不可跨查询比较。

字段解释：candidate_context 判 true 的确切标准

一个布尔字段，贴在每个片段上，含义就一句："下一阶段（事实规整）要不要读这一块。" true ＝ 读，false ＝ 跳过。 3,399 个里只有 415 个是 true——这就是它存在的全部意义： 省下对 88% 无关全文做技术和会计处理的工作量。

它不表示这块内容是真的、可信的、重要的。规则原文： "选择状态只表示与研究问题的相关性，不判断真实性、信源等级、内容类型或证据资格；检索命中不表示事实成立。"

两条路，满足任意一条即为 true

路径 A · 直接命中 DIRECT_HIT（四个条件全部满足）

2且命中该子查询至少一个 anchor_token硬过滤，实测刷掉 53.2%
3且在截断后活下来同一材料最多 5 条 → 全局 Top 20（第 20 名同分全保留）。防止一份 500 页年报把候选集全占了
4且自己不是结构噪声见上面那块折叠区

路径 B · 邻接扩展 ADJACENT_CONTEXT

某个直接命中的前后紧邻各一块也会被拉进来，但要同时满足：同一份材料、同一个 section、自己不是表格、那个直接命中的也不是表格、自己不是结构噪声。

为什么要邻接：文字有上下文。命中段可能写着"这一变化主要由以下因素驱动"，而真正的因素列在下一段。只捞命中段会把话读断。
为什么表格不扩展：表格是自足的——自带表头、单位、脚注，前后那张表跟它没关系，硬扩展只会拖进无关内容。

阶段 1–2 最容易被误解的一点

这两个阶段从头到尾没有任何一个环节在判断"内容对不对"。 但它们输出的东西，看起来全都像质量评分：

你看到的你可能以为它说它实际只说了

正确的心理模型是：这是一条证物链的保管流程，不是质检流程。 它保证"这块石头确实是从那个现场、那个时间捡回来的，中途没被掉包"。至于它是不是凶器—— 这两个阶段一个字都没说，也不该说（ADR 0002 就是为此存在的）。

阶段 03 · normalize-research-facts事实规整

把片段里的每个数字拆成原子记录：值、单位、币种、缩放、期间、会计准则、审计状态全部分字段存。

这一阶段在干什么（一句话）

抄卡片。把 415 个候选片段里的每一句话、每一个数字，抄成一张张只讲一件事的卡片， 每张卡片背面写清「我是从哪份材料、哪一页、哪个表格、哪一句抄来的」。

抄卡片的人不许判断这句话是真是假、可不可信、能不能拿来下结论——那是下一阶段的事。 他只负责三件事：抄准（数字一位不差、原文原样留底）、 标清口径（这个数是什么指标、哪个期间、什么单位、什么会计准则）、 缺了就说缺（不猜、不补零、不模糊匹配）。

所以这一阶段的产出叫「事实（fact）」而不是「证据（evidence）」—— 事实只是「原文这么写的」，离「这话能支撑结论」还差整整一个阶段。

做什么
  1. 只处理 candidate_context=true 的 415 个片段，不对无关全文做技术和会计处理。
  2. 技术标准化：把每个数字拆成主体 / 指标 / 值 / 单位 / 币种 / 缩放 / 期间 / 报告类型 / 原文定位，分字段存，同时保留原始值。
  3. 会计规整：逐字段独立判定会计准则、合并范围、审计状态、报告版本与重述关系——不打包继承。
  4. 桥接复算：按固定方向 CAS→IFRS 复算调节表，结果作为附着在目标事实上的核验记录，不新建来源事实。

这一阶段可以保存非权威的内容类型提示，但 claim_type 必须一律保持 UNASSESSED—— 最终内容类型、信源等级和证据资格由下一阶段决定。

这一步拦住了什么

  • 浮点数——可解析值一律用十进制定点字符串 + Decimal 计算，不得使用 JSON/二进制浮点数。 百分比以原显示数值配 unit=PERCENT 保存，不静默改为小数比率； 百分点用 unit=PERCENTAGE_POINT。
  • 把空白当零——每个数值必须有 value_status： PRESENT / EXPLICIT_ZERO / NOT_APPLICABLE / NOT_REPORTED / UNPARSEABLE / UNKNOWN。 只有原文明确为零、或表格图例明确说明破折号代表零且该图例可定位时才能用 EXPLICIT_ZERO。 空白、破折号、N/A 不得自动转为零。
  • 模糊匹配指标名——指标和主体只通过固定版本映射表规范化。 禁止字符串相似度、词干推断、停用词删除、Embedding 或模型语义归并。 没命中已确认别名就是 UNMAPPED，不猜。
  • 「映射成功 = 可比」——可比性必须绑定明确的比较对象，单独存 comparability_status 和固定原因码。不得保存没有比较对象的笼统可比状态。
  • 运行时自由公式——系统派生只允许固定白名单的 9 个公式，每项实现为固定函数 + 规则 ID。 不建设公式 DSL，不接受运行时自由公式。
  • 晶圆口径互换——8 寸 / 12 寸 / 8 寸等效不是单位缩放。 除非原文明确给了换算规则，否则禁止互换。利用率只保存来源披露值，不用产能与出货反推。

一句原文，切出几条事实？

规则很简单：每个 span（切出来的一小段原文）固定产 1 条文本记录，里面每出现一个数字再各产 1 条数值记录。

散文的情况

为什么两个数字都是 UNMAPPED：别名表里有毛利率、营业利润率， 没有光秃秃的「利润率」。系统坚持说「我不知道它指的是毛利率、净利率还是营业利润率」—— 这正是「宁可漏也不猜」的代价。加一行别名就能认出来，但那等于替原文做了决定，而原文确实没说清。

表格的情况：没有专门的切法

表格片段的正文被渲染成「行用换行分隔、单元格用制表符分隔」的纯文本，然后走同一个切句函数。 切句会在换行处切，所以——一个表格行 ≈ 一个 span。下面是快照里一个真实的表格片段 （CHUNK_6d1025bfe43ff31939eb6859，2023 年报第 16 页主要财务指标表）：

实测：normalization_run_status = WARN

WARN 的来源是那 4,912 条 PARTIAL——原始内容和定位可以安全保存，但部分规整属性是 UNKNOWN， 只能用于不依赖缺失字段的用途。每一条都登记了对应的 gap。

字段解释：metric_id 是什么，为什么它是杠杆最长的一个字段

一句话：metric_id = 「这个数字到底在度量什么」的标准化名字。 原文里同一个东西有一百种写法——revenue / total revenue / 收入 / 营业收入—— metric_id 把它们全部归一到一个固定的机器名 REVENUE。

白板版：会计口径 / 单位期间 / IFRS-CAS 桥接，这三件事各自在解决什么

这三个词经常被混为一谈，其实是三个层次的问题。

① 会计口径 —— 解决「这两个数是不是同一把尺子量的」

同一个公司、同一年、同一个「归母净利润」，可以有两个都正确的数：

2024 归母净利润 CAS 口径: 3,698,665 千元 IFRS 口径: 3,517,877 千元

差 18 万千元，两个都对，差异不是错报，是准则差异（联营企业股权被动稀释等调整项）。 所以会计准则必须进「可比键」——不同准则的数根本不构成冲突，因为它们本来就不是同一件事。 同理还有合并范围（合并 vs 母公司）、审计状态（审计 / 审阅 / 未审）。

② 单位 / 期间 —— 解决「同一把尺子的读数怎么对齐」

陷阱例子处理
量纲表头「单位：千元」，正文写 2,577,275，实际是 25.77 亿元缩放因子和换算结果两个都存
币种A 股报表千元、港股报表千美元没有冻结汇率就一律不换算，并列展示
期间YTD 累计 vs 单季 vs 财年 vs 半年期间类型显式存，不靠报表名推断
晶圆口径8 寸 / 12 寸 / 8 寸等效不是单位缩放，原文没给换算规则就禁止互换

晶圆口径这条值得多说一句：一片 12 寸的面积约等于 2.25 片 8 寸， 但公司用的等效系数是不是 2.25、是不是按产能加权，原文不说就不许自己乘。 利用率也只保存来源披露值，不用产能与出货量反推。

③ IFRS-CAS 桥接 —— 解决「跨准则时，公司自己给的换算自不自洽」

前两件事解决「能不能比」和「怎么比」，桥接解决第三件事：公司自己披露的那张调节表，算不算得平。 A 股年报里公司会给一张表：

按中国企业会计准则的净利润 ← row_role: BASE + 联营企业股权被动稀释等调整 ← row_role: ADJUSTMENT_DETAIL（只有这一类进求和） = 调节后小计 ← row_role: SUBTOTAL = 按国际财务报告准则的净利润 ← row_role: TARGET

规则文件靠四条中文关键词认出这四种行角色，然后按固定公式复算一遍，跟披露的目标值比。 只有 ADJUSTMENT_DETAIL 进求和——防止明细、小计、总计被重复计入。

实测 7 条：4 条 PASS（差异恰为 0）、3 条 UNKNOWN（输入口径不匹配，按规则不猜容差）。 这是整条链上唯一能主动发现披露内部矛盾的机制——但它只对公司自己给了调节表的那几个指标有效。

白板一句话：会计口径解决「能不能比」，单位期间解决「怎么比」，桥接解决「跨准则时官方的换算表能不能自己走通」。

深入：IFRS / CAS 桥接与政府补助敏感性

桥接只实现一个方向

CAS_TO_IFRS，公式固定为 IFRS_TARGET = CAS_BASE + sum(normalized_signed_amount of ADJUSTMENT_DETAIL)。 不接受运行时反向复算。每行标 row_role=BASE|ADJUSTMENT_DETAIL|SUBTOTAL|TARGET， 只有 ADJUSTMENT_DETAIL 进入求和——防止明细、小计和总计重复计入。

复算差异恰为零 → PASS；非零但在容差内 → ROUNDING_DIFFERENCE；超出容差 → FORMULA_MISMATCH。 容差固定为 0.5 × (各行 rounding_increment 之和)，不猜容差： 若任一必要披露精度缺失，则只有差异恰为零可 PASS。

实测 7 条：4 条 PASS，3 条 UNKNOWN（口径不匹配无法计算）。

政府补助敏感性：实测 0 条

只有当政府资金确认金额可分离、可追溯，与报告的 profit from operations 在期间、主体、准则、 合并范围、币种上一致，并能证明已计入该营业利润时，才允许计算敏感性。

阶段 04 · govern-and-validate-research-evidence证据治理

给每条事实定信源等级、内容类型、同源组和可用状态。这一层决定谁能承重。

这一阶段在干什么（一句话）

盖章。上一阶段抄好的 20,114 张卡片，这里给每张盖三种章： 这张卡片来自什么级别的信源（T1–T4）、 它属于哪种主张（既成事实 / 管理层说法 / 管理层指引 / 第三方观点）、 它能不能当承重墙用（可用 / 受限 / 隔离）。

盖章的人不许改卡片上的内容——一个数字都不改、一条记录都不删。 他只回答一个问题：「这张卡片，下游允许怎么用？」

所以这一阶段的产出叫「证据（evidence）」——事实是「原文这么写的」，证据是「这话你可以怎么用」。 同一句话，出自年报还是出自电话会，事实一模一样，证据资格天差地别。

「承重」到底是什么

定义：如果一条结论的方向直接依赖某条证据，那这条证据就是「承重」的。

白板上最好用的例子——管理层在电话会上说：「产能利用率显著改善。」

  • ✅ 可以写进报告：「管理层称产能利用率显著改善」——这是引用，CITE_ONLY 就够
  • ❌ 不能作为支撑：「产能利用率确实改善了」——这是承重，需要 CITE_AND_BEAR

区别在于：前者报告的是「有人这么说」这个事实，后者报告的是「事情就是这样」这个判断。

规则文件里有句注释点破了整个设计：没有单独的「可承重」布尔字段，因为 USABLE 本身就是这个意思。 一个概念一个字段，不搞两套可能打架的状态。

而且承重还要再过一关：即使证据是 USABLE，它的 metric_id 还必须在阶段 5 的承重指标白名单里， 才能定结论方向。实测下来 D2/D5/D7 的白名单是空的、D3 只有一条—— 这就是为什么最终 D1–D7 是 5 个 MIXED + 2 个 UNKNOWN，一个 SUPPORTED 都没有。

这一步拦住了什么

  • 让来源观点承重——这是最重要的一条。 承重的定义是「结论方向直接依赖它」。 管理层说「利用率显著改善」可以写进报告（标为 MANAGEMENT_ASSERTION）， 但不能成为「利用率确实改善了」的支撑。
  • 转载冒充多来源——同一份原始披露的不同入口算一个来源组。 转载不增加确认数量，证据分只按独立同源组计。
  • 定位断链——原始材料缺失或无法建立内容定位的记录不能成为可用证据， 也不能以 T4 代替（「来源差」和「找不到出处」是两回事）。

三个「不是」——这是最容易被误读的一处

  • 不是可信度。规则文件第一段注释原文写着 source_tier reflects only originality and traceability, not truth。 T1 年报里照样有抽错的数——反例那一页那条被读成「折旧 1,400 元」的记录，就是 T1。
  • 不是重要性。SIA 的行业销售数据是 D5 周期维度唯一的外部锚，但它仍然是 T2， 因为它不是发行人发的。

「查 20 行固定材料表」——真的就是字典查表

为什么敢这么写：因为快照冻结了，永远就是这 20 份。 20 份材料的场景下写规则引擎是纯粹的浪费——这是 AGENTS.md「Demo 简约」原则的直接产物。

tier 覆盖 是什么意思

tier 就是等级，「覆盖」就是用记录级判断推翻材料级默认值。全项目只有一条这样的规则：

record_tier_overrides: ai_summary_downgrade: to_tier: T4 applies_when_speaker_in: [ALPHASPREAD_AI_SUMMARY] applies_when_section_startswith: "AI Summary"

为什么需要它：AlphaSpread 那份电话会纪要整体是 T3（第三方转写，还算忠实记录了别人说的话）。 但这份文档里夹了一块 AI 自动生成的摘要——那不是转写，是机器改写， 中间多了一次可能失真的加工。所以同一份 T3 材料里，那几十条记录要单独降到 T4。实测降下来 89 条。

关键约束：合法状态断言里有一条 t4_only_for_ai_summary—— T4 只能出现在 AI 摘要记录上，别处出现 T4 就是非法状态，整个运行 FAIL。 这个「覆盖」机制被死死限制在一个场景里，不是一个可以随便用的降级通道。

注意这是记录级覆盖，不是材料级——同一份 T3 材料里，只有 AI 摘要那几十条降到 T4， 其余转写内容仍是 T3。T1–T4 各自是什么、凭什么分，见上面正文那一节。

判定顺序：材料类别优先于记录类型

材料是第三方转写（电话会纪要）？ ├─ 是 AI 摘要块 → THIRD_PARTY_VIEW（同时 tier 降 T4） ├─ 发言人是 OPERATOR → THIRD_PARTY_VIEW（主持人不是管理层） ├─ 前瞻（四条判据任一） → MANAGEMENT_GUIDANCE └─ 其他 → MANAGEMENT_ASSERTION 材料是行业协会 → THIRD_PARTY_VIEW 材料是指定媒体全文转载 → REPORTED_FACT（转载的是法定原文） 材料是发行人法定披露 → REPORTED_FACT

顺序为什么必须这样：电话会上 CFO 念的「毛利率 22.5%」，记录类型是「数值观察」， 如果按记录类型判就会变成 REPORTED_FACT——那等于把管理层口头说的数字升格成了法定披露。 所以必须先看「这是什么材料」，再看「这是什么记录」。

「前瞻性」怎么判：四条判据，任一命中即算

字段中文为什么它意味着「前瞻」
target_period陈述所指向的期间 跟「这句话是什么时候说的」是两回事。CFO 在 2026 Q1 会上说「预计下季度改善」—— 发言时间是 Q1，指向期间是 Q2。这个字段非空就说明在谈别的期间，绝大多数是未来
period_nature期间的性质 DURATION 一段时间 / POINT_IN_TIME 时点 / FUTURE 未来。等于 FUTURE 直接就是前瞻
uncertainty_text原文里的不确定性措辞 「约」「大致」「预计在…之间」「取决于市场情况」被单独抽出来存。 有不确定性措辞 = 说话人自己都没把它当成既成事实
前瞻词表兜底 扫 19 个词：expect / anticipate / outlook / guidance / forecast / next quarter / full year / going forward / 预计 / 预期 / 指引 / 展望 / 有望 / 目标 / 计划 / 将会 / 未来

前三条是结构信号（上游已经解析成字段了，可靠），第四条是词表兜底（不可靠，但能捞回一些）。

为什么非要分 GUIDANCE 和 ASSERTION

管理层说「上季度产能利用率是 92%」　→ MANAGEMENT_ASSERTION 管理层说「预计下季度利用率将改善」　→ MANAGEMENT_GUIDANCE

第一句错了叫「披露不实」（可核验、可追责）；第二句错了只叫「预测没准」（本来就不保证）。 混成一类，报告里就没法区分「公司说过什么」和「公司承诺过什么」。

ANALYTIC_INFERENCE 恒为 0 是一条硬闸门

它在合法状态断言里被写死为 analytic_inference_forbidden: true—— 一旦有任何记录带这个类型，状态组合合法性检查直接 FAIL，整个运行判定失败。

它在说的是：这个系统不生产自己的推论，然后把推论当证据再喂给自己。 系统能做的只有「引用别人说的话」和「按白名单公式算」。 这是为了防止「模型编了一个数 → 这个数变成了证据 → 下一步基于这个证据得出结论」这种自我强化的闭环。 而且是用状态断言硬拦的，不是靠约定。

深入：冲突检测为什么只覆盖 2 条事实

ADR 0003 把冲突检测限制在人工核对过的 fact_id 白名单上， 白名单目前只有 2 条用户确认的 FY2024 利润事实。

代价很直接：CONFLICT_UNRESOLVED 这条受限理由在 20,114 条里几乎不可能触发 （数据也印证了——4,912 条 RESTRICTED 全部由上游 PARTIAL 触发，另外两条理由一次都没独立触发过）。 「多来源冲突检测」这个能力在真实数据上等于没开。

这是有意识的取舍，不是 bug：全量冲突检测要先解决「什么算同一个指标的同一个期间」， 而那正是这个 Demo 刻意不去建通用框架的地方。代价是这个能力展示不出来， 报告第九章的冲突计数确实是 0，并附了一句说明这是 Snapshot v3 的真实承载力。

被排除在冲突检测之外的记录，按原因分：文本命题超出范围 15,539 / 缺 metric_id 3,499 / 缺可比性键 800 / 不在白名单 274。

它跑在谁身上、什么叫「同一件事」

跑在证据上（本阶段），但白名单是按 fact_id 认人的。 因为冲突判定同时需要两类信息：可比键那 10 个字段在事实里， 而内容类型、同源组、信源等级是证据阶段才有的。

可比键 10 个字段必须全等才算同一件事：

主体 · 指标 · 期间起 · 期间止 · 期间类型 · 会计准则 · 合并范围 · 币种 · 单位 · 内容类型

注意审计状态不在可比键里——审计状态不同不代表说的不是同一件事， 它只在消解排序时起作用。消解顺序七步：可比性 → 资格 → 同源去重 → 重述优先 → 审计状态 → 法定披露优先 → 信源等级。 绝不平均、绝不静默择一；没有唯一赢家就是 CONFLICT_UNRESOLVED，两个版本都保留、都不可承重。

实测的漏斗

候选事实 71 ← 有指标、有完整可比键的数值记录 合格事实 2 ← 白名单只放行 2 条 可比组 2 比较对 0 ← 每组只有 1 条，凑不出一对 检出冲突 0

冲突检测白名单（2 条）承重指标白名单

那 274 条「不在冲突白名单」的记录里，绝大多数是 T1 / REPORTED_FACT / USABLE / 可承重—— 它们完全有资格进报告承重。报告里 85 行证据表，绝大部分就是这类记录。

为什么只有 2 条能进冲突白名单

规则文件里写了原因：UPSTREAM_PERIOD_CLASSIFICATION_UNRELIABLE——上游的期间标注不可靠。 这不是抽象担心：D3 那条唯一的承重数值就是活例子，它被标成「2025 财年」， 但其实来自半年报。

如果放开跑冲突检测，这种记录会跟真正的年度数据落进同一个可比组， 然后系统会兴高采烈地报告「发现冲突：同一年的 ASP 有两个不同的值」—— 那是一个纯粹由标注错误制造出来的假冲突。阶段 3 那张表格里 「19.3% 和 38.0% 期间都是 UNKNOWN」也是同一个病。

而「人工核过」的标准高到什么程度：白名单里每条要写全 8 项签名， 核验时逐项比对，任一不符就整体失败。为什么不靠 fact_id：ID 是内容哈希， 万一哈希算法或字段集变了，光凭 ID 就可能把人工批准挪到一条完全不同的记录上。 全签名比对让「人工核准」绑定的是内容而不是标识符。

费曼三问：把这一步讲给第一次接触项目的人

1 · 输入和输出：像一场只能带指定资料进场的开卷考试

输入不是“整个互联网”或“整份快照随便读”，而是阶段 4 已治理的证据、对应上下文、既有 gaps 和 analysis.yaml。输出则分成四份：给模型看的封闭考卷 analysis-inputs.jsonl；七个初版结论 findings.yaml； 所有答卷（包括不及格答卷）analysis-attempts.jsonl；以及脚本的验收单 analysis-validation.yaml。

2 · 方法：先封卷，再答题，最后机读判卷

先封卷：脚本按固定检索分数、来源多样性和字符预算选资料； 再答题：模型只可判断方向、挑支持/反证、写限制和缺口； 后判卷：脚本检查引用、因果、禁词、管理层表述位置和评分规则，并反算分数。 模型不能看集合外材料、不能给分、不能给总分、不能跨维度凑论据。

3 · 数据结构：一份候选清单，加七份结构化结论

JSONL 适合“一行一条候选记录”；YAML 适合“一个维度一棵结论树”。二者用 evidence_id 相连：模型选的是 ID，脚本沿 ID 回查证据资格、来源组和期间， 而不是相信模型写出的数字或分数。

先选卷：不是把七个维度的候选集一起塞给模型

analysis-inputs.jsonl 这个文件确实装着 D1–D7 的全部候选集， 但它更像七个贴好标签的文件袋。脚本生成模型上下文时按 dimension_id 过滤：判断 D2 只取 D2 的 CANDIDATE_CHUNK 和 CANDIDATE_EVIDENCE， 不会顺手把 D1、D3–D7 或全部 20,114 条治理证据一起交给模型。

每个文件袋怎么装

  1. 文本按 chunk 选，不按零碎命题选：先让最多 3 个不同同源组各占一个位置，再按固定检索分数从高到低填充。
  2. 文本预算：目标 60,000 字符，允许最多 10% 的必要超出；同时最多 64 个 chunk。碰到第一个装不下的高分 chunk 就停止，不偷偷跳过去捡更短的低分片段。
  3. 数值另走一条路：该维查询命中的全部 USABLE 数值都保留，不占文本预算；白名单外的数值会明确标成 bearing=NO，只能作背景。
  4. 选择结果可复算：入选、跳过、最低入选分和规则参数都写进第一行 SELECTION_SUMMARY，并形成 selection_hash。

“同源组”不是材料数，而是原始披露的家族编号

公司网站版本、交易所入口和媒体全文转载，可能看起来是三份材料；如果它们都来自同一份原始公告， 就共享同一个 source_group_id，统计时仍然只算一个同源组。 这相当于同一张试卷复印十份仍然只有一份原件，防止“转载越多，证据越强”的假多源。

字段在候选集选择里怎么读
source_group_id当前 chunk / 证据属于哪一个原始披露家族，例如公司原文与指定媒体全文转载可同属 SG_SMIC_2026_Q1_DISCLOSURE。
available_source_group_count预算裁剪前，这个维度一共有多少个不同同源组可选。
source_group_count预算裁剪后，最终入选的文本 chunk覆盖多少个不同同源组。D1 是 12 个可选、最终覆盖 7 个；D2 是 12 个可选、最终覆盖 12 个。

同源组不同，只能说明“不是同一原始披露的重复入口”，不自动等于不同机构已经独立验证。 例如公司 2025 年报和 2026 Q1 公告可以是两个组，但仍都来自公司披露。

再分清三个 ID：metric_id 不是 evidence 的类型

原文标签 "gross margin / 毛利率" ↓ 阶段 3 按 rules/accounting.yaml 的固定别名表映射 metric_id: GROSS_MARGIN # 测量的是什么指标 fact_id: FACT_... # 规整后的这一个原子事实 ↓ 阶段 4 做信源、内容类型和使用资格治理 evidence_id: EVID_... # 完成治理后的这张证据卡 evidence_status: USABLE ↓ 阶段 5 检查 GROSS_MARGIN 是否在本维白名单，并让模型引用 EVID_...

metric_id 在阶段 3确定性生成，不是阶段 5 模型起的名字。 例如固定规则把 gross margin / 毛利率 映射成 GROSS_MARGIN；匹配不到就保留 metric_id=null 和 metric_mapping_status=UNMAPPED， 不让模型猜。

字段它回答的问题例子
metric_id这条数值测的是什么？GROSS_MARGIN、REVENUE。一个指标可在不同期间对应许多 evidence_id。
record_kind这条记录的数据形态是什么？NUMERIC_OBSERVATION / TEXT_PROPOSITION
claim_type来源内容是什么性质？REPORTED_FACT / MANAGEMENT_ASSERTION
evidence_status治理后允许怎样使用？USABLE / RESTRICTED / QUARANTINED

因此白名单里的六个 metric_id 是“允许承重的六种指标”，不是六条具体 evidence。 一条具体数值还要同时满足：属于本维候选集、状态 USABLE、被模型选进支持证据并通过引用校验，才真正参与方向和评分。

一次完整的模型沟通由两部分组成：固定任务说明告诉模型本维问题、允许字段、禁止事项和 “诚实回答 UNKNOWN 也是正确答案”；单维证据包则列出本维可见的数值证据、文本命题、 evidence_id、同源组、期间、口径和是否可承重。

四种 finding 只说“方向”，0–3 分另说“这个方向有多扎实”

finding模型什么时候这样答最容易混淆的地方
SUPPORTED可用证据总体支持本维命题，反证不足以推翻。不是“公司很好”，也不等于高证据分。
NOT_SUPPORTED存在可承重的反向证据，明确不支持或支持相反结论。没找到正面证据不等于 NOT_SUPPORTED；那通常是 UNKNOWN。
MIXED正反两面同时成立，例如年度改善、最近季度回落，单一方向会失真。MIXED + 3 完全合法：强证据证明情况确实混合。
UNKNOWN证据缺失、不可比、无方向或冲突无法解释。分数 0 必须 UNKNOWN；但有若干方向不明的证据时也可以是 UNKNOWN + 1/2。

这四种状态没有“正面证据满三条就自动 SUPPORTED”的脚本阈值，方向属于有界模型语义判断。 脚本只机械约束证据边界；证据分则由脚本另行反算。

最后判卷：findings.yaml 不是模型原样输出

模型先交的是 findings-attempt-*.yaml 里的单维答卷。 脚本取第一次通过门禁的答卷，补上可复算字段，再把七维汇总成正式 findings.yaml。所以它是“通过验收的模型判断 ＋ 脚本派生字段”，不是原始模型文本的简单复制。

模型负责脚本负责模型明确不能负责
finding、结论文字、支持/反证 ID、替代解释、限制、gaps、管理层口径，D7 的观察指标 验引用、验因果与禁词；补 fact_id、反算证据分及依据、记录尝试次数和白名单、汇总七维 证据分、加权总分、跨维综合评级、投资建议，以及候选集之外的新证据

单次答卷先过六道即时门禁

  1. 结构：字段只能来自固定 schema，维度 ID 和 finding 枚举必须合法；D7 还必须有观察指标。
  2. 引用：每个 evidence_id 必须存在、属于本维候选集且状态为 USABLE。
  3. 禁止输出：扫描交易指令、仓位、目标价、估值锚、投资吸引力和系统预测。
  4. 因果归因：出现“导致、驱动、因而”等因果词时，同一句必须说明是谁披露或主张。
  5. 管理层口径位置：MANAGEMENT_ASSERTION 不能混进 supporting_evidence 冒充已验证事实。
  6. 状态绑定：脚本试算为 0 分时，模型只能回答 UNKNOWN。

脚本能证明什么，不能证明什么

它能证明“模型只引用了允许的证据、输出没有越过机械边界、分数按固定公式得到”； 不能证明模型对原文的语义理解一定正确，也不能证明 SUPPORTED 一定是最佳结论。 这种内容层面的薄弱点留给阶段 6 的反方质询攻击。可核验在这里的含义是“过程和引用可检查”，不是“机器已经证明结论为真”。

“D1 盈利能力变化”“到底改善了没有？”可读报告脚本的固定维度标题与提问，不是模型临场生成。
“证据方向不一致”脚本把 MIXED 按固定字典翻成中文；MIXED 本身是模型的方向判断，之后还可能被阶段 6 降级。

承重指标白名单及中文名称白名单来自 rules/analysis.yaml；其中的 metric_id 源于阶段 3；中文只是一层展示注释，机器 ID 保持不变。
结论叙述模型生成的 finding_statement，但阶段 7 会把含未逐一绑定数字的句子整句排除，只展示留下的句子。
其他可能的解释模型生成的 alternative_explanations，同样经过整句数字过滤。
本维度的局限 / 缺什么数据模型生成的 limitations / gaps，随后由脚本做禁词和未绑定数字扫描。
证据卡片中的数值、期间、单位、来源从 normalized-facts.jsonl 与 governed-evidence.jsonl 原样读取，不由报告模型重写。

一句话：报告不是“模型写一篇文章”，而是模型研究文字 + 脚本计算与排版 + 治理证据字段的组合。 阶段 7 不重新调用模型，也不重新判断 D1。

这一步拦住了什么

  • 引用候选集外的证据——candidate_set_closure 校验，违反直接判失败。 即使模型凭记忆或猜测写出集合外的 evidence_id，脚本也会拒绝。
  • 模型自己给分——证据分由脚本从选中证据反算。分 0 强制 UNKNOWN； 反之不成立。无加权总分，overall_score 恒为 NOT_APPLICABLE。
  • 没标来源的因果措辞——causal_attribution 校验。 实测拦下了 3 次，全是同一个词：「因而」。
  • 用白名单外的指标承重——每个维度只有名单内的 metric_id 能承担结论方向。 D2 / D5 / D7 名单为空，D3 只有一条，如实披露不修补。
  • 无限重试到通过为止——每维最多两次生成机会，第二次再失败就强制 UNKNOWN + 证据分 0 + 整个阶段 FAIL。

附录 A · 数据长什么样只读输入

不可重建的冻结产物：删掉就再也回不来。每个文件贴一段真实数据，配一张字段速查表。 这里只讲「长什么样、字段是什么意思」，为什么这么设计请回各阶段页看。

本页所有样本直接取自黄金案例的实际文件：只做截断、排版压缩和加注释， 不改写任何字段名与取值（英文原文保持英文，不译）。… 表示此处有省略。

先记住两条通用约定

① 业务 ID 就是溯源链

material_id → chunk_id → fact_id → evidence_id → finding_id → challenge_id ，另有 gap_id 挂在链上。不设通用的 artifact_id / run_id / case_id； 版本由 snapshot_id ＋ 文件哈希 ＋ manifest 表达。

② 三种格式各有分工

  • YAML — 单例配置、汇总、状态、规则引用（case.yaml、各种 *-validation.yaml）
  • JSONL — 逐条记录，一行一个对象（材料、片段、事实、证据）
  • Markdown — 只有一个：给人读的 report.md

时间一律 ISO 8601 带时区；数值的值、单位、币种、缩放分开存，不把单位拼进数字字符串； 缺失一律 UNKNOWN / TBD ＋ 记 gap，不得用空串、0 或模型估计顶替。

容易混的区别
canonical_locator_source_class vs 信源等级 T1–T4 前者是阶段 1 选哪个入口当权威（ISSUER / 监管 / 具名机构 / 其他）； 后者是阶段 4 判这份材料多可信。同一份材料可以入口权威但信源等级不高
acquisition_targets vs matched_query_ids 前者是采集登记："我为什么把这份材料放进来"； 后者是检索结果："这一块文字真的谈到了什么"。实测两者不重合—— 登记为 ASP 的材料 6 份，D3 族真正命中的材料 13 份
candidate_context vs evidence_status 前者是阶段 2："下一步读不读"；后者是阶段 4："能不能引用、能不能承重"。 进候选 ≠ 可用证据
normalization_status vs evidence_status 前者是阶段 3："口径填全了没"；后者是阶段 4："能不能用"。 PARTIAL 会机械地变成 RESTRICTED（4,912 = 4,912），但反过来不成立—— RESTRICTED 还可能来自低信源等级或冲突未决
metric_mapping_status vs 承重指标白名单 前者是阶段 3："这个数是什么指标"；后者是阶段 5："这个指标能不能顶结论方向"。 MAPPED 只是入场券——D2/D5/D7 的白名单是空的，那三维再多 MAPPED 也承不了重
conflict_eligibility 白名单 vs 承重指标白名单 两个完全不同的白名单。前者管"能不能拿去互相比对"（2 条），后者管"能不能顶结论"。 不在冲突白名单 ≠ 不能进报告——那 274 条大多是 T1 / USABLE / 可承重
